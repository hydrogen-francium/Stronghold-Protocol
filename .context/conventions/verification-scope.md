# 功能推进与验证范围

## Context（上下文）

2026-10-21，用户追加要求：**不要钻测试的牛角尖**。本规约用于限定接手、开发和排错时的验证投入，修正此前优先收敛全部历史测试失败的接手计划。

## Fact / Pitfall（事实与问题）

- 测试用于发现当前功能风险，不是独立于产品目标的交付物；历史失败清零不是默认接手目标。
- 夹具、测试基础设施或环境限制的失败不能未经核实等同于业务缺陷，也不能以此无限扩展排查范围。

## Solution / Convention（执行规约）

1. 优先推进用户当前需要的功能和实际可用主流程，不把全量测试通过作为每一步开发的前置条件。
2. 验证限于当前改动的关键路径和直接风险，优先使用已有针对性测试、必要的静态检查或实际操作；不为了追求覆盖率扩建测试体系。
3. 对与当前交付无关、历史遗留或短期无法定位的失败，记录复现条件、已知影响和未确认项，然后继续推进；不无假设地反复重跑、扩大矩阵或深挖平台内部行为。
4. 明确阻塞主流程、账号隔离、数据完整性或安全边界的问题仍需优先处理。确实无法继续时，明确报告阻塞点，不绕过风险冒充完成。
5. 不通过删除断言、随意跳过用例、放宽阈值、吞错或更新黄金结果来制造通过；未验证范围照实说明。
6. 发布或提交前按既有仓库要求安排完整验证；若无法通过则报告失败与交付边界，不把该要求扩展成日常开发期间必须先清空所有历史失败。
7. 同一问题连续两轮“定位—修改—定向验证”仍未解决，停止自动深入，记录复现、已知影响和后置建议。区分当前开发阻塞、上线阻塞与环境或补充验证，不让后两类阻塞所有后续开发。
8. 用户已于 2026-10-21 默认同意按主计划继续本地实施，不要求中途阶段性汇报或再次确认下一步；实际完成后一次说明改动、验证与剩余边界。此约定不授权提交、推送、外部发布、真实部署或掩盖失败。
9. 同日用户进一步明确授权完成后本地提交，并由用户手动部署；测试修改和新增测试不提交。此后提交范围按 `source-delivery.md` 执行，仍未授权推送或真实部署。
